# Warren threat model

Status: written 2026-10-22 against `main` at `de49e96` (PR #36).
Review this whenever a runtime, credential path, or route that touches a workspace changes.

## Premise: the agent is hostile

Warren runs coding agents (Claude Code and, later, other harnesses) inside workspaces.
The design assumes the agent and everything it can write are hostile. A prompt injection
in a repo, issue, web page or dependency can make an otherwise well-behaved agent act
against its operator. Treat the following as attacker-controlled:

- every process inside the workspace, and anything they can spawn;
- every file the workspace can write: the checkout, `.git/`, rc files, harness state, and
  anything on the workspace's EFS access point, from earlier task launches too;
- project and template config once it has been persisted and read back (`spec_json`),
  because it may predate a validator.

Warren's own processes are trusted: the CLI on the user's host, the control plane
(`warren-server`), and the materialization step that runs before the agent.

## Assets

| Asset | Where it lives | Who may hold it |
|---|---|---|
| Host filesystem outside the workspace (`~`, `~/.ssh`, `~/.aws`, other repos) | user's machine / podman host | user only |
| Host harness config (`~/.claude`, settings, credentials) | user's machine | user; workspace gets scoped, mostly read-only views |
| Project secrets (`secrets.env`, SSM parameters) | host / SSM | only workspaces whose template declares them |
| GitHub App private key | OS credential store (local issuer) or Secrets Manager (control-plane issuer) | the issuer only; never a workspace |
| GitHub installation tokens | minted per workspace, 1 hour | that workspace's git credential helper |
| git-crypt key | operator | materialization step only, and only with `git_crypt: unlock_and_drop` |
| AWS credentials | host SSO session; ECS task roles | template's single profile (local `export` mode); the minimal task role (ECS) |
| Model access (Bedrock today) | AWS credentials / proxy secret | the harness, scoped to specific models |
| Operator's Claude login (OAuth tokens) | host Keychain / `~/.claude/.credentials.json` | the operator; a subscription-mode workspace gets a per-launch copy of the access token only, a Bedrock-mode workspace gets nothing |
| Control-plane API tokens | CLI config, server DB | users; workspace-scoped machine tokens for agents |
| Other users' workspaces and secrets | control plane, ECS, EFS | their owner |
| Control-plane IAM role and infrastructure | ECS service, IaC | the control plane only (#3) |
| Audit trail | structured logs (`event="audit"`) | read by operators; written only by the control plane |

## Trust boundary per runtime

| Runtime | Boundary | Strength | Notes |
|---|---|---|---|
| **seatbelt** (macOS, `sandbox-exec`) | SBPL profile generated by warren, invoked by absolute path (AE2), profile and state kept outside the workspace | **Mistake containment, not a security boundary** | `lsopen`, `mach-lookup`/`mach-register`, `iokit-open` and `distributed-notification-post` stay open (see [SECURITY.md](../SECURITY.md#known-limitations)); full network. Do not run an untrusted agent here expecting host isolation. |
| **bubblewrap** (Linux) | user/pid/uts/ipc namespaces, bind mounts limited to the workspace and declared paths, `--die-with-parent` | Medium | Network is shared with the host (`--share-net`); same kernel. |
| **nsjail** (Linux) | namespaces including a fresh, interface-less network namespace (`clone_newnet`), seccomp policy, config regenerated from the persisted spec into warren's state dir on every connect | Medium–high | Same kernel; no network unless configured. |
| **docker / podman** | container: separate mount/pid/net namespaces, bind mounts only for the workspace and declared folders (`ro` where declared); server-side podman is rootless | Medium–high | No east-west path between workspaces: each podman workspace has its own `isolate`d bridge (`<egress_bridge_name>-<id>`, used for egress byte counting, removed on destroy, orphans pruned at startup, workspaces still on the old shared bridge migrated at startup); docker workspaces join `warren-isolated`, a bridge with inter-container communication off. A podman workspace's SSH port is published on `127.0.0.1` only (`WARREN_SSH_PUBLISH_HOST`), and containers can't reach host loopback, so other workspaces can't reach it; docker workspaces publish nothing. Outbound traffic is unrestricted. Templates' `docker_networks` attach extra, shared networks by design. |
| **ECS Fargate** | **the task itself.** Firecracker micro-VM per task, minimal task role, EFS access point per workspace | High against the host; **none inside the task** | See the residual risks below. |

### Orchestrator → workspace traffic

The orchestrator never dials the sidecar. All orchestrator→workspace traffic uses the
runtime's own authenticated control channel: podman API exec or the ECS Exec relay,
container logs, and host-side state files read without following links. The sidecar is an
in-container helper on a root-only Unix socket. If the orchestrator needs structured data
from inside a workspace, it runs a command through the control channel (which may talk to
the local socket) and reads the output. No runtime has an inbound network listener on
a workspace.

`GET /workspaces/{id}/files`, `/files/{path}` and `/diff` work this way: the server runs
the image's `warren-query` script with a fixed argv. The only caller-supplied value is a
validated relative path, passed as its own argv item. The script drops from root to the
workspace user (`warren`, else `nobody`) and never follows a symlink below the root. Its
output comes from inside the workspace, so the server parses it strictly, re-applies the
exclusions and caps its size. The script's git calls ignore system and global config and
pin `core.fsmonitor`, hooks, external diff and textconv off. The workspace's own repo
config still applies, but only as the workspace user, inside the workspace.

### ECS Fargate

Verified 2026-10-18 on platform 1.4.0: `unshare -U`, `bwrap` and every `--unshare-*` flag
fail with `Operation not permitted`, `SYS_ADMIN` is rejected at `RegisterTaskDefinition`,
and `NET_ADMIN` is unavailable. There is no in-task sandbox, and no way to hide the
credentials endpoint `169.254.170.2` from the agent. So:

- **Everything inside a workspace task is agent-controlled**, including any warren helper
  or sidecar in the same task. Nothing goes into a task that the agent must not have.
- **The workspace task role is the control and stays minimal**: EFS ClientMount/ClientWrite
  and the ECS Exec channel. Interim exception, documented: direct Bedrock needs
  `bedrock:InvokeModel*` scoped to exact model/inference-profile ARNs in one region, as a
  separately named statement to remove when the model proxy lands.
- Per-workspace secrets go through task-definition `secrets` (execution role), never the task
  role. The task-definition cache is keyed by the whole canonical definition, including
  every `valueFrom`, so one owner's SSM ARN is never reused for another.
- Clone credentials are given only to the `git-init` container (#29). It copies them into
  private files, re-execs with an empty environment, clones into a private dir, deletes the
  credentials, and only then touches the volume. The workspace container depends on it
  finishing and never receives them.
- No plan should add an in-task bwrap/nsjail layer. Runtime detection on Fargate is
  GuardDuty Runtime Monitoring plus CloudTrail alerting on the task role (AF1, deployment
  IaC, deferred).

## Threats and controls

| # | Threat | Control | Where |
|---|---|---|---|
| T1 | Config `mount:` path (absolute, `..`, symlinked parent) makes warren delete or link outside the workspace | `FolderSpec` validator accepts only normalised relative paths; containment re-checked after `realpath` right before every `rmtree`/symlink, so old persisted specs are covered too | #31 |
| T2 | Agent rewrites its own sandbox policy for the next connect | nsjail config and seatbelt profile live in warren's out-of-tree state dir and are regenerated from the persisted spec on each connect; profiles are parameter-based, not string-built (#34) | #31, #34 |
| T3 | Agent plants `.git` config/hooks (`core.fsmonitor`, hooks, `ext::`) that host-side git then runs | One shared safe-git helper pins `core.hooksPath=/dev/null`, `core.fsmonitor=false`, `protocol.ext.allow=never` on every host-side git call; `.git` rename protection in the sandbox (AE1); `git-materialize.sh` uses the same pins, rewrites reused bare-store config from scratch, and never fetches into agent-written repos | #31, #34, #29 |
| T4 | PATH hijack of the sandbox binary itself | `sandbox-exec`/`bwrap`/`nsjail` invoked by absolute path (AE2) | #34 |
| T5 | Workspace gets every project secret, not just its template's | Local provisioning filters `secrets.env` to the template's declared names and errors on missing ones; ECS uses per-name SSM `secrets` | #31, #29 |
| T6 | Host `~/.claude/settings.json` env (API keys etc.) leaks into workspaces and rc files | Implicit import removed; env comes only from template `env:` / `secrets`; `~/.claude` grants scoped per harness, mostly read-only | #31, #34, #36 |
| T7 | Agent steals the SSO token and mints credentials for every AWS account/role | AWS `export` mode: host runs `aws configure export-credentials` for the template's one profile and serves it over a local endpoint; no `~/.aws/sso` grant. `sso` mode only for interactive local `kind: user` workspaces, with a warning | #34 |
| T8 | Long-lived GitHub PAT in the workspace is exfiltrated | GitHub App installation tokens per workspace, limited to the template's repos and `contents`/`pull_requests`, 1-hour lifetime, delivered by a git credential helper (not env, URLs or `.git/config`); local issuer (OS keychain) or control-plane issuer (Secrets Manager, unreadable by the task role) | #33 |
| T9 | git-crypt key decrypts history or leaves with the agent | `git_crypt: none` by default; `unlock_and_drop` unlocks in materialization and deletes the key before the harness starts | #33 |
| T10 | One user acts on another user's workspace (connect, exec, destroy, token, git credentials) | Every workspace route checks the server-resolved owner (`403 not workspace owner`); agents use workspace-scoped machine tokens that can't touch other workspaces; token TTL and admin revoke | #33, earlier PRs |
| T11 | Workspace task assumes the control plane's IAM role or reaches orchestration APIs | Separate, minimal workspace task role; control-plane role not passable to workspaces (#3) | #3 |
| T12 | Clone over SSH is MITM'd | GitHub host keys baked into ecs-base (`ssh_known_hosts`), unknown host keys fail closed; weekly check against `api.github.com/meta` | #29, this PR |
| T13 | Unreviewed harness upgrade changes agent behaviour, or a tampered binary | Harness versions pinned exactly in every Dockerfile; ECS dev base verifies the binary against Anthropic's GPG-signed release manifest; base images pinned by digest; weekly bump PRs gated on smoke tests | this PR |
| T14 | Duplicate or orphaned tasks keep running (cost, stale access) | Transitional ECS states map to `starting`; idempotent `RunTask` with `clientToken`; orphan sweep; `delete()` purges EFS data | #30 |
| T15 | Repudiation: no record of who issued a secret or token | Structured `event="audit"` records for secret write/delete/delivery, provision/connect/destroy, credential issuance; caller identity from the server, never the client; secret values rejected as fields | #33 |
| T17 | An agent driving warren over MCP provisions, execs in or destroys workspaces beyond its own | `/mcp` sits behind the same AuthMiddleware; each tool calls the REST handler (owner check, audit). A workspace-scoped token's tools only take its own workspace id; only a reservation token (`POST /workspace-tokens`) can provision, exactly once, the id the server chose for it. After a single-turn completion the token can only read status/events and make the idempotent destroy call. Exec output and time are capped (`WARREN_EXEC_MAX_*`) | this PR |
| T18 | Agent steals the operator's Claude login, or uses it to bypass a template meant to run on Bedrock | The sandbox can't read the Keychain or host `~/.claude`. In subscription mode, warren copies in the access token without the refresh token on each connect, so a stolen copy expires and a sandbox refresh can't rotate the host's token. In Bedrock mode (`model_access: bedrock`, or `CLAUDE_CODE_USE_BEDROCK`/`ANTHROPIC_BEDROCK_BASE_URL` in env), warren reads no Keychain item, deletes any earlier copy, rejects a `CLAUDE_CODE_OAUTH_TOKEN` secret, and only connects with the workspace's own AWS credentials (`export` endpoint locally, task role on ECS) | this PR |
| T16 | Data exfiltration over the network | **Observed, not blocked.** Podman egress byte counters feed the idle reaper only (D-05). Fail-closed egress (NET-01) is future work; see residual risks | — |

## Known residual risks

1. **Seatbelt is not an isolation boundary.** See the runtime table. Use podman or ECS for
   untrusted work.
2. **Open egress everywhere except nsjail.** An agent can send anything it can read
   (checkout, scoped secrets, its own tokens) to any host. Controls limit *what* it can
   read and for how long tokens work, not where it can send them.
3. **ECS credentials endpoint.** `169.254.170.2` is reachable from the agent, so it holds
   the task role's credentials (and Bedrock access while the interim direct-Bedrock path is in use).
   Mitigated only by keeping the role minimal.
4. **Vendor cloud handoff.** Some harnesses can hand a task to the vendor's own cloud
   (for example Cursor's `&` background/cloud agent). The code and prompt then leave
   warren's boundary entirely, with the vendor's credentials and network. Warren can't
   sandbox that; harness profiles (AG1) should disable or refuse such modes where the
   harness allows it.
5. **Symlink races (TOCTOU).** The workspace-deletion containment check runs immediately before `rmtree`
   and symlink creation, but a workspace process running concurrently can still swap a
   path component between the check and the operation, on any object warren operates on
   in a workspace-writable tree. Destroy-time operations should run when the workspace is
   stopped, and `*at()`/`O_NOFOLLOW` style operations would close the gap.
6. **Host-level reachability for docker/podman.** Workspaces can't reach each other's
   container IPs, published SSH ports, or services the host binds on `127.0.0.1`
   (integration-tested for rootless podman via the gateway, `host.containers.internal`,
   `10.0.2.2`, `169.254.1.2` and the host's own IP). What remains:
   - Anything the host listens on at a non-loopback address (`0.0.0.0`, its LAN IP, the
     docker bridge gateway) is reachable from workspaces like from any LAN client. That
     includes other containers' ports published on `0.0.0.0` and, if
     `WARREN_SSH_PUBLISH_HOST` is set to a non-loopback address, other workspaces' SSH
     ports (the per-workspace key is then the only barrier). Bind host services to
     loopback or firewall them from the container subnets.
   - Rootless podman keeps host loopback closed by default. Setting slirp4netns
     `allow_host_loopback=true` or pasta `--map-gw`/`-T` in `containers.conf` reopens it.
   - Docker Desktop and colima route `host.docker.internal` (colima: `192.168.5.2`) to
     the desktop host, whose `localhost` services, including ports the VM forwards, are
     then reachable from workspaces. Warren can't close that from inside the VM.
   - Templates' `docker_networks` are shared by design.
   Each podman workspace uses one /24 from the netavark subnet pool, which bounds
   concurrent podman workspaces per host (about 255 with the default pool).
7. **Same kernel for bwrap, nsjail, docker and podman.** A kernel exploit escapes all of
   them; only Fargate's micro-VM is a separate kernel.
8. **Deployment-wide GitHub App repo allow-list** (`WARREN_GITHUB_APP_ALLOWED_REPOS`): any
   authenticated user can mint tokens for any listed repo. One server per trust boundary.
9. **Local GitHub App issuer key exposure.** Whoever holds the key mints for every repo the
   App is installed on. Acceptable for a single operator; team deployments use the
   control-plane issuer only.
10. **Runtime threat detection is not in place** (AF1, deferred).
11. **Images built FROM a bumped base by digest** (`warren-agent-base`,
    `warren-ecs-agent-base`) lag a harness bump until the base is republished and the digest
    updated.
